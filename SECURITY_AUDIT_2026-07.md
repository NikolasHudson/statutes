# Security & SOC 2 Readiness Audit — Fresh Full Audit

**Date:** 2026-07-07  ·  **Threat model:** external attackers (unauthenticated + authenticated remote users abusing the public REST API, the live `corpus.nick.law/mcp` MCP endpoint, and the Next.js frontend).

**Method:** multi-agent workflow `security-audit-soc2-fresh` — 9 parallel finder agents across security dimensions (auth/session, authz/tenancy, injection, MCP, secrets/config, frontend, data-exposure/logging, supply-chain, transport/DoS), **every finding independently re-verified against the current code by a skeptic agent instructed to refute it**, then synthesized. 42 agents total; 1 finding dropped as a false positive.

## Executive summary

From an external-attacker perspective the platform's most acute exposure is the public MCP endpoint (corpus.nick.law/mcp): it authenticates an X-API-Key but skips every authorization, quota, rate-limit, input-size, and audit control that the REST API enforces, so any self-minted free-tier key yields unbounded, unlogged, cost-amplifying access to paid tools — an economic and availability DoS on a single-instance service. The next tier of risk is systemic vulnerability-management and change-management drift: production runs an EOL Django 5.1 branch and an EOL Node 20 base image with a structurally broken auto-patch path, and every push to main auto-deploys five components with no test/build gate. No critical remote-code-execution or authentication-bypass was confirmed; the dominant patterns are missing rate-limiting/quotas, client-controlled inputs trusted for security decisions (XFF, Host), and confidentiality/retention fixes that exist only in the uncommitted working tree and are therefore not deployed.

> **No critical, no remote code execution, and no authentication bypass was confirmed.** The dominant patterns are missing rate-limiting/quotas (especially on MCP), security decisions made on client-controlled inputs (X-Forwarded-For, Host), end-of-life runtimes with a blocked patch path, and confidentiality/retention fixes that exist only in the **uncommitted working tree** and are therefore not deployed.

## Cross-cutting themes

- MCP transport is a second-class citizen: it authenticates the X-API-Key but bypasses every authorization, quota, rate-limit, input-size, and audit control the REST API enforces — the single highest-leverage gap, converging findings across authz, dos, and logging dimensions.
- Rate-limiting, quotas, and input-size caps are absent across the cost/compute endpoints (MCP search/audit tools, unbounded text, verify-document budget), enabling cheap cost-amplification and single-instance availability DoS.
- End-of-life and unpinned-drift runtime/dependency risk with a structurally broken auto-patch path: EOL Django 5.1, EOL Node 20, digest-frozen OS images, and Dependabot bounds/ecosystems that can never propose the supported versions.
- Security decisions are made on client-controlled inputs: the left-most X-Forwarded-For entry drives throttle keys and audit IPs, and the spoofable Host header drives tenant/product scope resolution.
- Confidentiality and retention controls for privileged legal data exist only in the uncommitted working tree (VerificationRun purge/redaction, per-user localStorage scoping), so the deployed product violates its own stated posture until those fixes are pushed.
- Weak change-management and detection foundation: push-to-main auto-deploys with no test gate, mutable-tag actions, and no durable audit trail for API-key auth outcomes, so a regression or key compromise can ship and run undetected.

### High

#### 1. Public MCP endpoint enforces no rate limiting or tier quota, enabling cost-amplification DoS
- **Severity:** High · **Confidence:** — · **Category:** dos · **SOC 2:** CC6.1 · **Exploitability:** remote-authenticated
- **Location:** `backend/apps/mcp_server/auth.py:81`
- **Merged:** also reported as — MCP server enforces no rate limiting, quota, or per-key throttling. _Reported by two independent finder dimensions (authz + dos). The rate-limit half of the MCP feature-gate finding is the same root gap._
- **Issue:** The live MCP server at corpus.nick.law/mcp authenticates every request with X-API-Key (apps/mcp_server/auth.py:api_key_middleware) but applies NO rate limit, no per-key daily quota, and no tier feature-gate. The docstring is explicit: 'rate limiting, audit logging - both deferred for now' (auth.py:10-11), and .do/app.yaml:248 confirms 'Auth today is X-API-Key only (no rate-limit/audit yet)'. This is asymmetric with the REST API, where every endpoint calls _gate() -> require_feature() + enforce_rate_limit() (apps/api/api.py:152-157, apps/api/auth.py:106-150, TIER_DAILY_QUOTA free=200). On MCP, search_statutes is dispatched with rerank=True and use_vector=True by default (apps/mcp_server/server.py:113-122), and search_statutes_tool -> retrieve_context runs a paid Voyage query embedding plus a paid Voyage cross-encoder rerank pass per call (corpus_tools.py:58-101). Any registered user can self-mint an API key (account_router create-key, session-auth only) and then call MCP tools without limit. The MCP service also runs instance_count:1 (.do/app.yaml:260), so there is no horizontal headroom to absorb a flood.
- **Attack scenario:** Attacker registers a free account (registration throttled only per-IP/hour), creates an API key, and scripts high-frequency POSTs to https://corpus.nick.law/mcp calling search_statutes (or audit_brief). Each call triggers paid Voyage embedding + rerank API spend and heavy DB/vector work with zero per-key ceiling, running up an unbounded third-party bill and saturating the single MCP instance to deny service to legitimate MCP clients. The REST TIER_DAILY_QUOTA that would cap this is bypassed entirely on the MCP transport.
- **Fix:** Enforce the same per-key quota + tier feature-gate on the MCP transport that the REST API uses: in api_key_middleware (or a wrapping ASGI layer) call enforce_rate_limit()/require_feature() for the resolved APIKey before dispatching to FastMCP, and return 429 on exceed. Back the counter with the shared Redis cache (as chat/REST already do) so it holds across the MCP workers, and add audit logging of MCP tool calls.
- **Verifier note:** Every claim checks out against current code.

1. No rate limit/quota on MCP: auth.py:46-84 api_key_middleware only verifies X-API-Key (verify_key at line 75) then sets scope["mcp_api_key"] = api_key and passes through (line 81-82). No quota, tier gate, or rate-limit call anywhere. The docstring (lines 9-10) states "rate limiting, audit logging — both deferred for now." grep for enforce_rate_limit/require_feature/rate_limit across apps/mcp_server/ returns nothing.

2. Paid work per call: server.py:113-122 registers search_statutes with defaults use_vector=True and dispatches to search_statutes_tool with rerank=True. tools.py:58-102 (search_statutes_tool) calls retrieve_context with use_vector and rerank. use_vector=True drives vector_search which embeds the query via voyage (search.py:37 imports default_client/INPUT_TYPE_QUERY). rerank=True selects default_reranker() which returns a real VoyageReranker whenever VOYAGE_API_KEY is set (rerank.py:101-104, class VoyageReranker at 63). app.yaml confirms the mcp component inherits VOYAGE_API_KEY (line 243), so in prod both the embedding and cross-encoder calls are live paid Voyage spend — two paid third-party calls per request with no ceiling.

3. Self-service key minting: accounts.py:519 create_key is auth=session_auth; any logged-in user can mint an API key. So the attack requires only a registered account (authenticated), not privileged access.

4. Asymmetry with REST: api.py:151-157 _gate() runs require_feature() + enforce_rate_limit(); auth.py defines TIER_DAILY_QUOTA (line 32). The MCP transport bypasses all of this.

5. Single instance / no headroom: app.yaml:260 instance_count: 1, with an in-file comment (line 236-239) "Keep instance_count: 1 until a shared store (Valkey) backs cross-instance rate limiting" and line 248 "Auth today is X-API-Key only (no rate-limit/audit yet)".

The vulnerability is real and reachable: an authenticated user can script unbounded high-frequency MCP calls, each triggering paid Voyage embedding + rerank spend and heavy DB/vector work with no per-key cap, running up third-party bills and saturating the single MCP instance. Not a false positive — no missed mitigation exists (transport_security only guards Host/Origin/DNS-rebinding, not volume; auth only checks key validity).

Severity: I keep this at high but flag exploitability as remote-authenticated (not remote-unauthenticated) since a self-minted key is required, though that barrier is trivial. The cost-amplification angle (unbounded paid API spend triggered cheaply) plus single-instance saturation justifies high rather than medium; the authentication requirement is the only thing holding it back from critical.

### Medium

#### 2. Registration throttle and audit source IP trust the client-controlled left-most X-Forwarded-For entry
- **Severity:** Medium · **Confidence:** — · **Category:** auth · **SOC 2:** CC6.1 · **Exploitability:** remote-unauthenticated
- **Location:** `backend/apps/accounts/audit.py:121`
- **Merged:** also reported as — Audit-trail source IP is attacker-forgeable: client_ip() trusts the left-most X-Forwarded-For entry. _Identical code defect (client_ip reads split(',')[0]) reported under two impacts — throttle bypass and audit-IP forgery. One fix resolves both; keep the higher (medium) severity._
- **Issue:** client_ip() reads the source IP as the LEFT-MOST entry of X-Forwarded-For (`xff.split(",")[0]`). Behind the DigitalOcean App Platform proxy the platform APPENDS the real client IP to any inbound XFF, so a request the attacker sends with `X-Forwarded-For: 1.2.3.4` produces `1.2.3.4, <real-ip>` and client_ip() returns the attacker-supplied `1.2.3.4`. This value is used as the throttle key in _register_throttle (apps/api/accounts.py:306, `register:ip:{ip}:...`) and as the persisted audit `source_ip` (audit.py:151/159). An unauthenticated attacker rotating the header value gets a fresh throttle bucket on every request, defeating the 10/hour registration cap entirely (the very control added to stop mass account creation / email-enumeration probing), and can forge or hide their IP in the security audit trail. Note the axes login-lockout path is NOT affected because it uses django-ipware with AXES_IPWARE_PROXY_COUNT=1, which correctly discounts the trusted proxy hop — this custom helper does not.
- **Attack scenario:** Attacker scripts POST /api/auth/register with a random `X-Forwarded-For` header per request (e.g. incrementing 10.0.0.N). Each distinct value is a new `register:ip:{ip}` cache bucket, so the 10-per-hour cap never trips and they can create thousands of accounts or run email-enumeration/duplicate probes unthrottled; the audit rows record the spoofed IPs, poisoning forensics.
- **Fix:** Derive the client IP the same way axes does: use django-ipware (or replicate AXES_IPWARE_PROXY_COUNT logic) to take the entry `proxy_count+1` from the right of XFF, not the left-most. Share one trusted-proxy-aware helper between audit.py, _register_throttle, and any other rate-limit key so the platform hop is discounted consistently.
- **Verifier note:** The vulnerable code is present exactly as reported. audit.py:121-125 (`client_ip`) reads `HTTP_X_FORWARDED_FOR` and returns `xff.split(",")[0].strip()` — the LEFT-MOST entry — with a docstring that incorrectly assumes "left-most entry is the original client." Standard XFF semantics (and the DO App Platform proxy) APPEND the connecting client's IP to any inbound header, so a request carrying `X-Forwarded-For: 1.2.3.4` becomes `1.2.3.4, <real-ip>` and the helper returns the attacker-controlled `1.2.3.4`. The real client IP is the right-most/second-from-right hop, not the left-most.\n\nThis is corroborated in-repo: the codebase's own axes config (core/settings.py:213-214) sets `AXES_IPWARE_PROXY_COUNT = 1` with `AXES_IPWARE_META_PRECEDENCE_ORDER = ["HTTP_X_FORWARDED_FOR", "REMOTE_ADDR"]`, i.e. django-ipware is told to discount exactly one trusted proxy hop from the right — the correct behavior for a single appending proxy. The custom `client_ip` helper does not do this hop-discounting, so it trusts spoofable input while the login-lockout path does not (matching the finding's note).\n\nReachability confirmed: `client_ip` feeds `_register_throttle` at accounts.py:306, which builds the cache key `register:ip:{ip}:{hour}` (accounts.py:307) and enforces `_REGISTER_MAX_PER_HOUR = 10` (accounts.py:300/315). Rotating the XFF value yields a fresh cache bucket per request, defeating the 10/hour cap. The same tainted IP is persisted as `AuditEvent.source_ip` (audit.py:151/159) and logged, poisoning the forensic trail. The /register route uses `auth=csrf_protect`, but CSRF is not a barrier to a scripted attacker: /csrf is public (auth=None, accounts.py:330) so an attacker fetches a token+cookie and submits matching values — CSRF only blocks cross-origin browser forgery, not a direct client. axes covers /login but not /register (the endpoint is not an authenticate() call), so this cache counter is the ONLY registration rate control, and it is fully bypassable by an unauthenticated remote attacker.\n\nSeverity medium is accurate: impact is throttle bypass enabling mass account creation / repeated enumeration probing plus audit-log IP forgery. It is not higher because unique-email enforcement + the generic duplicate-email response (accounts.py:349-360) limit it to a weak enumeration oracle, and no data compromise or auth bypass results. But it is a genuine remote-unauthenticated defeat of a deliberately-added security control, so it is not a cost-free best-practice nit. Fix: use django-ipware (as axes already does) or index from the right by trusted-proxy count instead of taking split(",")[0].

#### 3. Sign-out ignores logout response: failed logout renders as success while the session cookie stays valid
- **Severity:** Medium · **Confidence:** — · **Category:** auth · **SOC 2:** CC6.1 · **Exploitability:** local-or-privileged
- **Location:** `chat-frontend/components/auth-gate.tsx:153`
- **Issue:** The signOut handler POSTs /api/auth/logout but never checks the response status: `await fetch(...)` is followed unconditionally by clearThreadStores(), setStatus("signed-out"), and setUser(null). If the logout request returns non-2xx — e.g. a 403 because csrfHeaders() resolved to {} (ensureCsrfToken returns null when the /api/auth/csrf bootstrap fails, and csrf.ts explicitly documents that the request 'will then fail the server's CSRF check'), or a transient 502 from App Platform — the UI still transitions to the signed-out sign-in screen while the Django session cookie remains valid. There is no user-visible error and no retry. Conversely, if fetch() throws (network drop), the await rejects and BOTH the localStorage thread wipe and the UI state reset are skipped; both call sites (app/(app)/shell.tsx:141 `onClick={() => void signOut()}` and components/app-sidebar-footer.tsx:99 `onClick={signOut}`) swallow the rejection silently.
- **Attack scenario:** Attorney on a shared firm/library machine clicks Sign out; the logout POST fails (CSRF bootstrap failure returning 403, or a 5xx during a deploy). The screen shows the sign-in page, so the user walks away believing they are signed out. The next person at the keyboard reloads the page; AuthGate's GET /api/auth/me succeeds with the still-valid session cookie and they are signed in to the victim's account — full access to chat, profile PATCH (email takeover), and API-key creation under the victim's identity.
- **Fix:** In signOut, capture the response and only treat sign-out as complete when r.ok (or 401). On failure, surface an error and keep the user signed in so they can retry. Move clearThreadStores() into a finally block so the local wipe happens even when the network call throws. Optionally hard-navigate (window.location.assign('/')) after a confirmed logout so no in-memory app state survives.
- **Verifier note:** The code is present exactly as reported. chat-frontend/components/auth-gate.tsx:153-165 awaits fetch("/api/auth/logout") with no response.ok check and no try/catch, then unconditionally runs clearThreadStores(), setStatus("signed-out"), setUser(null). The failure precondition is real: lib/csrf.ts csrfHeaders() returns {} when the /api/auth/csrf bootstrap fails, and the backend logout route (backend/apps/api/accounts.py:419, auth=csrf_protect; session_auth.py CsrfProtect) raises 403 before the handler runs — so on 403 (or any 5xx) the Django session cookie remains valid while the UI shows the sign-in screen as a successful sign-out. Both call sites (app/(app)/shell.tsx:141 `void signOut()` and components/app-sidebar-footer.tsx:99 `onClick={signOut}`) swallow rejections, so a network throw also skips the localStorage thread wipe silently. AuthGate's mount effect (line 112) then re-authenticates anyone who reloads via GET /api/auth/me on the surviving cookie. The code's own comment (lines 159-161) states the shared-machine threat model this violates. No mitigation exists. However, exploitation requires a silent logout failure plus physical access to the same browser by another person — an opportunistic local scenario, not remotely triggerable — so medium is the correct severity; impact on success is full account takeover-equivalent access (chat, profile PATCH/email change, API-key creation).

#### 4. MCP tools bypass the tier-based feature entitlement gate enforced on the REST API
- **Severity:** Medium · **Confidence:** — · **Category:** authz · **SOC 2:** CC6.3 · **Exploitability:** remote-authenticated
- **Location:** `backend/apps/mcp_server/server.py:113`
- **Merged:** also reported as — Live MCP endpoint authenticates but skips tier feature-gating and rate limiting, letting any FREE-tier key call paid-only tools with no quota. _Same authorization root reported twice: the MCP middleware never calls require_feature, so a FREE-tier key reaches SOLO+ paid tools. Shares its fix with the HIGH rate-limit item._
- **Issue:** On the REST API, features are gated by tier via require_feature (apps/api/auth.py:96): FREE keys are limited to {'lookup','search'} while validate/history/at_date/cross_refs/definitions/amendments are SOLO+ only. - **Attack scenario:** A holder of a FREE-tier API key that is entitled only to lookup+search over the REST API points Claude Desktop / mcp-remote at corpus.nick.law/mcp and invokes audit_brief / validate_citations / list_recent_amendments, obtaining paid-tier functionality without entitlement — an authorization bypass that also undermines the billing/tier model.
- **Fix:** Read scope['mcp_api_key'] in each tool (or a shared dispatch wrapper) and call require_feature(api_key, <feature>) before executing, mapping each MCP tool to the same feature name used in FEATURES_BY_TIER.
- **Verifier note:** Verified against current code. REST API enforces tier entitlements on every endpoint via _gate() -> require_feature() (backend/apps/api/api.py:152-157; backend/apps/api/auth.py:42-56, 96-103): FREE keys are limited to {lookup, search} and get 403 on validate/history/at_date/cross_refs/definitions/amendments. Preconditions are realistic: users default to Tier.FREE (backend/apps/accounts/models.py:34) and any logged-in user can self-serve an API key via POST /api-keys (backend/apps/api/accounts.py:517-547); the HTTP MCP app is the production deployment target. The bypass is actually slightly broader than reported: MCP also skips enforce_rate_limit, so the FREE 200/day quota is unenforced too. Severity stays medium: impact is entitlement/billing-model bypass and unmetered compute (hybrid search + rerank), not exposure of non-public data (the corpus is public Iowa law) and no cross-user privilege escalation. Exploitation requires a valid API key, i.e. any registered free account, so remote-authenticated.

#### 6. Deployed prod never purges VerificationRun rows and stores raw client-identifying filenames (fix exists only uncommitted)
- **Severity:** Medium · **Confidence:** — · **Category:** data-exposure · **SOC 2:** C1.2, CC6.5, CC8.1 · **Exploitability:** local-or-privileged
- **Location:** `backend/apps/api/management/commands/purge_chat_traces.py:98`
- **Issue:** VerificationRun rows contain verbatim quote fragments lifted from users' uploaded legal documents (findings JSON: raw/span/resolution) plus the original upload filename. In the working tree, purge_chat_traces deletes both ChatTrace and VerificationRun and trace_capture redacts filenames via _redact_source_name(). However, ALL of these changes are uncommitted (git status: modified purge_chat_traces.py, trace_capture.py, models.py). Production deploys from pushed main (deploy_on_push: true in .do/app.yaml); at HEAD e9d655b, `git show HEAD:backend/.../purge_chat_traces.py` contains no reference to VerificationRun (only ChatTrace is purged), and `git show HEAD:backend/.../trace_capture.py` writes `source_name=source_name or ""` unredacted. ## Dropped / false positives

1 finding dropped after adversarial verification:

- **Live secrets exposed to the Docker build environment via RUN_AND_BUILD_TIME scope** (`.do/app.yaml`) — The spec facts are accurate: .do/app.yaml lines 36-44 and 54-56 scope SECRET_KEY, OPENAI_API_KEY, VOYAGE_API_KEY, and DATABASE_URL as RUN_AND_BUILD_TIME, and the Dockerfile (lines 39-42) proves the build needs no real secrets. But the claimed exposure mechanism does not exist for this app: every component (statutes, mcp, trace-purge, chat-frontend, docling) builds from a Dockerfile (app.yaml lines 168, 200, 216, 252, 287), and per DigitalOcean's documentation, Dockerfile-based builds on App Platform only receive env vars via docker build arguments, which require a matching ARG instruction in the Dockerfile to be visible to RUN steps — and bindable variables like ${iowa-db.DATABASE_URL} are explicitly runtime-only for Dockerfile builds. Grepping all three Dockerfiles shows zero ARG instructions (the sole 'ARG' match is inside a comment at Dockerfile line 35), so unconsumed build args are discarded by Docker/BuildKit and never appear in the environment of RUN pip install (Dockerfile line 26) or RUN npm ci. The claimed exploit (a poisoned package's setup.py hook exfiltrating OPENAI_API_KEY/DATABASE_URL during pip install) therefore cannot read the secrets — they are not present in the build environment. Tightening the scope to RUN_TIME (as already done for DOCLING_INTERNAL_TOKEN, line 52) remains sensible cost-free hygiene against a future buildpack switch or ARG addition, hence info rather than dismissal, but there is no present exposure.
